# НСД та запуск у Docker

## Що ми обчислюємо

НСД (найбільший спільний дільник) — найбільше додатне ціле число, на яке обидва числа діляться без остачі. Для 48 і 18 це 6. Для двох нулів додатного найбільшого дільника немає; у програмі домовляємося повертати 0, як math.gcd у Python.

Використовуємо алгоритм Евкліда: НСД(a,b) = НСД(b,a % b), поки b не дорівнює нулю. Тоді відповідь — a. Заміна зберігає спільні дільники: якщо a=q*b+r, то спільний дільник a та b ділить r=a-q*b; навпаки, спільний дільник b та r ділить a=q*b+r. Для невід'ємних чисел кожна ненульова остача менша за попередній дільник, тому цикл закінчується.

| Крок | a | b | a % b |
|---|---:|---:|---:|
| 1 | 48 | 18 | 12 |
| 2 | 18 | 12 | 6 |
| 3 | 12 | 6 | 0 |
| Завершення | 6 | 0 | Не обчислюємо |

`examples/gcd.c` спочатку робить від'ємні числа невід'ємними. `while (b != 0)` також захищає від остачі за нульовим дільником. Змінна remainder зберігає стару остачу до зміни a та b. Без неї легко помилитися через послідовність присвоєнь. `return a` повертає результат.

Програма-аналізатор не містить спеціальної команди «рахувати НСД»: вона розбирає звичайну програму C. В AST будуть program, block, declare, if, unary, while, binary(%), assign та return. Один обхід цього дерева виконує алгоритм, інший генерує Python. Значення a і b змінюються безпосередньо у gcd.c; scanf і введення з клавіатури ця підмножина не підтримує.

## Без Docker у Linux

```bash
python3 compiler.py examples/gcd.c --report
python3 build/generated.py
python3 tests.py
xdg-open build/ast.html
```

Для поточного examples/gcd.c обидва способи виконання мають дати 1 (35 та 64). Таблиця вище ілюструє іншу пару: 48 та 18. Для 270 та 192 — 6; для 35 та 64 — 1. Факторіал залишено як додатковий приклад, основний приклад — gcd.c.

## Docker

Docker може замінити окрему Linux VM для запуску цього проєкту, якщо викладач не вимагає саме VM. Контейнер використовує Linux і Python; це не повноцінна графічна віртуальна машина. HTML відкривається у браузері Windows після збереження результатів у спільну папку.

Потрібний встановлений і запущений Docker Desktop у режимі Linux containers. Для його WSL 2 backend потрібне налаштоване WSL 2 та підтримка віртуалізації. Перевір вимоги для свого комп'ютера: https://docs.docker.com/desktop/setup/install/windows-install/

У PowerShell перейди до розпакованої папки mini-c та виконай:

```powershell
docker version
docker build -t mini-c-lab .
New-Item -ItemType Directory -Force build | Out-Null
docker run --rm --mount "type=bind,source=$($PWD.Path)\build,target=/app/build" mini-c-lab
Start-Process .\build\ast.html
```

У Linux у папці mini-c:

```bash
docker build -t mini-c-lab .
mkdir -p build
docker run --rm --mount "type=bind,source=$(pwd)/build,target=/app/build" mini-c-lab
xdg-open build/ast.html
```

Образ запускає тести, аналіз gcd.c і згенерований код. `--mount` зберігає три результати у build на твоєму комп'ютері. parser.out залишається в одноразовому контейнері. Перше складання потребує інтернету для базового образу python:3.12-slim; PLY уже включено. Образ slim без фіксованого digest може змінюватись з оновленнями.

Якщо зміниш gcd.c, повтори docker build, бо вхідні файли копіюються у образ під час складання. Контейнеру не потрібні privileged, Docker socket, пароль або доступ до всього диска.

Асистент може виконувати ці команди, якщо docker доступний у його середовищі й Docker Desktop запущений. Самого повідомлення «доступ дозволено» недостатньо для створення технічного підключення. У середовищі, де готувався цей варіант, команда docker не знайдена, тому запуск контейнера ще не перевірено. Локальний запуск Python перевіряється окремо.

Офіційна довідка про монтування папок: https://docs.docker.com/engine/storage/bind-mounts/
